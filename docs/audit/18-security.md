# Security Audit — Бизнес с Контуром
Date: 2026-05-07  
Auditor: Security Engineer  
Scope: Client-only browser game, no backend, no auth

---

## 1. Storage

### What is persisted

| localStorage key | Content |
|---|---|
| `konturgame_state_v7` | Full `GameState` — game-mechanical values only |
| `konturgame_rollback_v7` | Snapshot of `GameState` for undo |
| `kontur_meta_progress_v1` | Cross-run stats: totalRuns, bestWeek, unlockedLessons |
| `konturgame_history` | Array of `{week, balance, isVictory, date}` |

### PII assessment

`GameState` includes `playerBackstory` (an enum pair: `motivation` + `personal`) and `npcs[].memory` (player-authored NPC memory entries). The backstory fields are enum values (`'corp' | 'accident' | 'hometown' | 'friend'`), not free text — no PII. NPC memory entries appear to be programmatic strings generated by the game engine, not user-entered text. No real-name, email, IP address, or payment data is ever stored.

**Finding S-1 (Low):** `playerBackstory` is a pre-selected enum value and does not constitute PII under GDPR/152-ФЗ. No action required for data minimisation. However, if a future version introduces free-text NPC notes or player names, that would elevate to PII.

### Load-time validation

`loadGameFromStorage()` (line 1436) calls `JSON.parse()` with no schema validation, then passes the result directly to `loadGame()`. `loadGame()` merges the parsed object over `createInitialState()` via spread (`{ ...createInitialState(state.businessType), ...state }`). This means:

- **Tampered numeric fields** (e.g. `balance: 9999999999`) are accepted as-is. No range checks are applied during load. The game-over check runs only during `processWeek()`, so an impossible balance will silently persist.
- **Tampered enum fields** (e.g. `businessType: 'hacker'`) skip the `BUSINESS_CONFIGS` key guard and will cause `undefined` dereferences on first use.
- **Extra keys** are stripped by `extractState()`, which whitelists field names — this is good practice and limits injection surface.
- **`rollback()` (line 916)** calls `JSON.parse(snapshot) as GameState` with a bare type cast and no validation at all before calling `set(state)`.

**Finding S-2 (Medium — DoS Self):** See Section 5 for full analysis.

## 2. Promo Code Trust Model

The three promo codes (`GAME-BANK-2026`, `GAME-MARKET-2026`, `GAME-ELBA-2026`) are hardcoded as plaintext in `src/constants/promoCodes.ts` (lines 16–33). Any player who opens DevTools will see them in the bundle immediately. The codes are revealed to the player as a reward for activating the corresponding in-game service — the reveal mechanism is entirely client-side.

### Is this a threat?

For this product, **no** — with an important caveat. The codes serve as marketing conversion tools: a player sees a code after activating Контур.Банк in the game and is meant to use it on the real Контур website. The threat model question is: does early discovery of the code (via DevTools) bypass anything of value?

- **In-game effect:** none. Knowing `GAME-BANK-2026` grants no in-game advantage; services unlock through gameplay progression.
- **Real-world offer value:** if the codes are published on the Контур website as live discount/trial codes, anyone who finds them in the JS bundle can redeem the offer without playing the game. This is the only material risk.

**Finding S-3 (Medium — Business Risk):** The promotional codes have real monetary value (e.g., "3 months free Elba"). They are fully exposed in the client bundle. If redemption is tracked on the server by the Kontour CRM, a determined user who extracts the codes can redeem the offer without ever playing the game. This is a marketing funnel bypass, not a security vulnerability per se, but represents a real budget/attribution risk.

**Recommendation:** If conversion tracking matters, the promo codes should be single-use tokens generated server-side and returned only after the player completes the in-game action (via a lightweight API call). For a low-cost alternative, use a publicly-known but finite-inventory code with a cap enforced server-side, and accept the minor leakage as an acceptable cost of a client-only architecture.

## 3. XSS Surface

A full-codebase grep for `dangerouslySetInnerHTML`, `innerHTML`, `document.write`, `insertAdjacentHTML`, and `eval` returned **zero results**. The codebase exclusively uses React's JSX rendering, which escapes all interpolated values by default.

**Finding S-4 (Info):** No XSS vectors identified. All user-facing dynamic content is rendered through React JSX string interpolation.

One noteworthy observation: `SettingsModal.handleExportState()` (line 27) calls `console.log('Game state:', data)` where `data` is the full JSON-serialised store. If an attacker could somehow inject a crafted save containing a very long string into a field rendered in DevTools, this is not exploitable in a standard threat model. The risk is negligible.

## 5. Persisted State Injection / DoS Self-Corruption

There are three `JSON.parse` paths from localStorage:

1. **`loadGameFromStorage()`** — wraps parse in try/catch; returns `null` on error. Safe against malformed JSON.
2. **`App.tsx` useEffect (line 21–35)** — reads from the old key `konturgame_state` (not `_v7`), wraps in try/catch, falls back to backstory screen. Safe.
3. **`rollback()` (line 916–921)** — `JSON.parse(snapshot) as GameState` with no try/catch. If the rollback snapshot is corrupted (e.g., browser storage was truncated by a quota error mid-write), this will throw an uncaught exception and crash the component tree.

Additionally, `loadGame()` (line 829) merges the persisted object over the initial state with no field-level type coercion or range clamping. Specific crash scenarios:

- `businessType: undefined` → `BUSINESS_CONFIGS[undefined]` returns `undefined` → spread operator throws on first property access.
- `services: null` → spread `...state.services` in any action handler throws.
- Injecting `employees: [{id: null, salary: "xss", efficiency: "abc"}]` causes `fireEmployee` to compute `NaN * 0.5` for severance — this won't crash but silently corrupts balance.
- Injecting `loans` array with a length of 100,000 items would not crash the game but would make every render slow (O(n) filter loops).

**Finding S-6 (Medium):** `rollback()` is missing try/catch around `JSON.parse`. A quota-truncated snapshot will crash the game. Fix: wrap in try/catch and call `clearRollback()` on error.

**Finding S-7 (Low — Self-only):** No schema validation on load means a player who manually edits their save can produce impossible game states. Since there is no server-side authoritative state and no other players are affected, the only victim is the player themselves. For a single-player promotional game this is acceptable, but `businessType` should at minimum be validated against the known enum values before the spread to prevent an immediate undefined-dereference crash.

**Key isolation note:** `extractState()` whitelists field names during save, which correctly prevents injected extra keys from being re-persisted. The attack window is only during the current session in memory.

## 6. Content Security Policy (CSP)

`index.html` contains no `Content-Security-Policy` meta tag or HTTP header configuration. Vite's config (`vite.config.ts`) does not configure response headers.

**Finding S-8 (Medium):** No CSP is defined. Without CSP, if an XSS vulnerability were introduced in a future commit, the browser would offer no additional defence layer. For a static SPA served from a CDN or web server, a CSP header should be added at the hosting layer.

Recommended baseline for this application (no external scripts, no inline eval, fonts/images self-hosted):

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data:;
  font-src 'self';
  connect-src 'none';
  object-src 'none';
  frame-ancestors 'none';
```

`'unsafe-inline'` for styles is required for React's inline `style={{}}` props used pervasively throughout the codebase. If inline styles were replaced with CSS classes, even that exception could be dropped.

**Note:** Since the current XSS surface is zero (Finding S-4), the CSP gap has no immediate exploit path. The priority is to add it before launch so it is present from day one.

**Finding S-9 (Info):** Zero external network requests are made by the application at runtime. From a privacy and supply-chain standpoint this is the best possible outcome for a client-only game. No third-party tracking is present.

## 8. Privacy Compliance (GDPR / 152-ФЗ)

### Data collection inventory

| Data | Location | Is PII? | Retention |
|---|---|---|---|
| Backstory enum pair | localStorage | No | Until save deleted |
| Game progress (balance, week, achievements) | localStorage | No | Until save deleted |
| Run history (week, balance, isVictory, timestamp) | localStorage | No | Until cleared |
| Meta progress (run count, bestWeek) | localStorage | No | Until cleared |

### Assessment

No personally identifiable information is collected or transmitted. All data lives exclusively in the local browser storage of the user's own device and is never sent to any server. There are no cookies, no user accounts, no IP logging.

**Under GDPR / 152-ФЗ:** Since no personal data is processed (the data never leaves the user's device and there is no server-side processing), the game does not constitute a "data controller" for the purposes of either regulation. No cookie banner, privacy policy, or consent mechanism is legally required for the current feature set.

**Finding S-10 (Low — Forward-looking):** If Яндекс.Метрика, Google Analytics, or any other analytics SDK is added in the future, this assessment changes immediately. Even pseudonymised analytics constitutes personal data processing under GDPR and requires a privacy notice, cookie consent banner, and a DPA with the analytics vendor. This should be reviewed before any analytics integration.

**Finding S-11 (Low):** The promo code share URL `konturgame.ru` is placed in clipboard text. If this URL is a real Kontour-owned domain, it may eventually have analytics that track referrals, which would constitute processing. No action needed now, but note the dependency.

**COPPA:** No age-gating mechanism exists. The game content is business-themed and not directed at children. However, if the game is published on a platform accessible to minors under 13 (US) or under 16 (EU), an age gate or explicit COPPA/GDPR-K statement may be advisable.

## 10. Recommendations

### Priority matrix

| ID | Severity | Finding | Action |
|---|---|---|---|
| S-8 | **P1** | No CSP | Add `Content-Security-Policy` header at hosting layer before launch |
| S-3 | **P1** | Promo codes hardcoded in bundle | Decision required: accept leakage as a known trade-off, or implement server-side single-use token generation |
| S-6 | **P2** | `rollback()` missing try/catch | Wrap `JSON.parse` in try/catch; call `clearRollback()` on failure |
| S-7 | **P2** | No `businessType` guard on save load | Validate `businessType` ∈ `['shop', 'cafe', 'salon']` before the spread in `loadGame()` |
| S-5 | **P3** | esbuild/vite dev-server CVE | Upgrade vite to ≥6.5.0 in a controlled upgrade window |
| S-10 | **P3** | No analytics privacy guard | Document the requirement: any future analytics integration needs GDPR review before merge |
| S-2 | **P3** | No range validation on numeric fields at load | Add lightweight clamps for `balance`, `reputation`, `loyalty` in `loadGame()` migration block |
| S-11 | **Info** | `SettingsModal` logs full state to console | Remove or gate behind a `DEBUG` flag for production builds |

### Detailed recommendations

#### R-1: Add CSP header (P1)

Configure the hosting server (nginx, CDN, GitHub Pages custom headers) to emit the CSP header listed in Section 6. If using Vite preview for staging, add it via `vite.config.ts` `preview.headers`. This should be done before the first public deployment.

#### R-2: Promo code architecture decision (P1)

Option A (current, acceptable for soft launch): Accept that codes are in the bundle. Inform the Kontour marketing team so they can set server-side redemption limits. Document the known exposure.

Option B (preferred if codes have real budget impact): Add a minimal serverless function (e.g., Cloudflare Worker, Yandex Cloud Functions) that accepts `{serviceId, sessionToken}` and returns a one-time code. The client never has the code until it is earned.

#### R-3: Fix rollback() crash (P2)

In `gameStore.ts` around line 916, wrap the JSON.parse in try/catch and call `clearRollback()` in the catch block to prevent a corrupted snapshot from crashing the game permanently.

#### R-4: Validate businessType on load (P2)

In the `loadGame()` action, before the spread, check:
```typescript
const VALID_BUSINESS_TYPES: BusinessType[] = ['shop', 'cafe', 'salon']
if (!VALID_BUSINESS_TYPES.includes(state.businessType)) {
  console.error('Invalid businessType in save, resetting')
  return // or set to default
}
```

#### R-5: Remove debug console.log from SettingsModal (P3)

`handleExportState()` in `SettingsModal.tsx` calls `console.log('Game state:', data)` which dumps the entire store to the browser console. This is a debug feature that should either be removed from production or gated behind a dev-mode flag. It poses no direct security risk (the user can see their own data) but could confuse users or be used for support-ticket misuse.
