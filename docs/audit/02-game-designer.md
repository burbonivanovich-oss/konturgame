## 1. Core Loop (processWeek — 7 дневных итераций)

### Структурная целостность

`processWeek` выполняет детерминированный 7-дневный цикл с накоплением результатов. Архитектурно цикл устойчив: нет goto-обходов, нет branch-утечек, нет состояния, которое читается до своего обновления внутри той же итерации.

**Сильные стороны:**
- Единственная точка входа: событие → `pendingEvent` → блокировка `checkWeekBlocked`. Игрок не может «проскочить» недели без решения события. Механизм надёжен.
- Конкурент-событие срабатывает ровно один раз в неделю (флаг `competitorEventTriggered`), а не 7 раз в цикле. Это был бы серьёзный баг в предыдущей редакции.
- `autoResolveExpiredDecisions` закрывает дедлайн-события первой не-Контур опцией — правильный default, поскольку игрок получает «наказание за безделье», а не бесплатный пропуск.
- Лояльность выше 70 имеет decay (−(loyalty − 70) × 0.10 в день) — правильный сдерживающий механизм, предотвращающий тривиальное «накопить до 100 и забыть».

**Структурные дыры:**

**Дыра 1 — Микрособытия без ветвления.** `applyWeeklyMicroEvent` всегда применяет `options[0]` без предоставления выбора игроку (`micro.options[0]` — первый и единственный вариант). Это пассивный нарратив, не механика. Игрок видит результат, но не принимал решения. Из 7 дней недели минимум 6 проходят без осмысленного выбора игрока.

**Дыра 2 — Pain Engine обнулён полностью.** `calculatePainLosses` возвращает нули для всех сервисов. Функция вызывается в цикле, но не имеет эффекта. `PAIN_LOSSES` в `gameBalance.ts` содержит числа, которые не используются нигде в runtime — только как мёртвая документация. Это означает, что единственный стимул купить сервис — это bundle-тир (rev%) + прямые эффекты сервиса (capacity, taxSaving и т.д.) + события, которые требуют сервис как опцию. Pain как непрерывный «кнут» полностью отсутствует.

**Дыра 3 — Контур.Банк бесплатен (`annualPrice: 0`).** Банк — обязательный для 40% платежей, не имеет годовой стоимости. Игрок никогда не сталкивается с trade-off «стоит ли платить за Банк». ROI Банка бесконечен. Это убивает экономическое напряжение первых недель.

**Дыра 4 — `LEVEL_TABLE` в `business.ts` содержит полную таблицу опыта (уровни 1–10), но `level`/`experience` были удалены в Phase A.** Мёртвый код вводит в заблуждение при чтении кодовой базы и должен быть удалён.

**Дыра 5 — Milestone-проверка запоздалая.** Веха week10 проверяется при `state.currentWeek === 10`, но `currentWeek += 1` происходит после проверки. То есть проверка фактически происходит по окончании 10-й недели (начало 11-й), что семантически правильно, но `pendingMilestoneCelebration` выставляется при `currentWeek === 11`. Это означает, что если игрок не достиг веху на неделе 10, он получит попытку снова на неделе 11 — но `milestoneStatus.week10` уже `false` и не обновится. Milestone missed — тихое поражение без явного UI-сигнала.

### MDA-проверка core loop

- **Aesthetics (цель):** Challenge (выживание) + Discovery (что делает каждый сервис) + Fantasy (я — предприниматель).
- **Dynamics:** Игрок балансирует расходы на сервисы против дохода, нанимает сотрудников, реагирует на события.
- **Mechanics → Dynamics соответствие:** Mechanics в целом порождают нужные Dynamics, но Discovery страдает: когда Pain Engine нулевой, игрок не «открывает» для себя ценность сервиса через боль — он читает описание в карточке. Это маркетинг, не геймплей.

## 2. Decision Density — осмысленность недельных решений

### Инвентаризация решений игрока за типичную неделю

| Действие | Частота | Осмысленность |
|---|---|---|
| Событие (pendingEvent) | 1 раз / нед | Высокая — реальные ветви с последствиями |
| Покупка сервиса | 0–1 раз / нед (онбординг) | Высокая — необратима, дорогая |
| Запуск рекламной кампании | По желанию | Средняя — ROI-расчёт |
| Найм/увольнение сотрудника | По желанию | Средняя |
| Улучшение бизнеса | По желанию | Средняя — необратима |
| Tier upgrade | 1 раз / ~12 нед | Высокая, редкая |
| Заказ склада | По желанию | Низкая — тривиальна при FIFO |
| Займ | Ситуативно | Средняя |
| Owner Investment | По желанию | Низкая |
| Микрособытие | 1 раз / нед | Нулевая (нет выбора) |

**Вывод:** В большинстве недель игрок принимает ровно 1 осмысленное решение (событие) плюс несколько управленческих опционально. В недели без событий игра полностью переходит в режим «нажать кнопку и посмотреть результат». Это симулятор-таймер с одним прерыванием в неделю.

### Сравнение с теорией

По **Self-Determination Theory** (Deci & Ryan): Autonomy требует, чтобы множество путей были жизнеспособны. Сейчас доминантная стратегия — подключить все 7 сервисов как можно быстрее, вложиться в capacity (Маркет + нанять персонал) и ждать tier upgrade. Альтернативные пути (без ОФД, без Диадока) не наказываются (Pain Engine = 0), но и не имеют особой поддержки. Игрок не сталкивается с настоящей дилеммой «какой сервис купить первым, если деньги ограничены».

По **Flow Model** (Csikszentmihalyi): саwtooth-кривая сложности должна строиться через кризисные события. Кризисы на неделях 10/20/30/40 — правильная идея, но только 3 кризис-ивента определено в `crisisEvents.ts`. Если все три уже triggered (oneTime: true), на неделе 40 `generateCrisisEvent` вернёт null, и игра тихо переключится на обычное событие. Это разрушает ожидаемый пик напряжённости.

## 3. Синергия и Pain Balance — кнут и пряник

### Текущее состояние

**Пряник (Bundle Tiers):**
- 3 сервиса: +10% revenue
- 5 сервисов: +20% revenue
- 7 сервисов: +30% revenue

Это единственная synergy. Все поля `calculateSynergyModifiers` кроме `revenueBonus` возвращают 0. Механика прозрачна и хорошо передаётся UI-виджетом «СПАСЕНО С КОНТУРОМ».

**Кнут (Pain Engine):** Полностью нулевой в runtime. PAIN_LOSSES в gameBalance.ts определяют тонко откалиброванные значения (Market: 4% revenue, OFD: 10% шанс × 15% revenue, etc.), но они нигде не вызываются в processWeek после обнуления painEngine.ts.

**Что осталось как «кнут»:**
1. Bank: без него 40% клиентов уходят (getBankPaymentRatio = 0.6) — это работает.
2. События: некоторые события имеют `noService: 'fokus'` — т.е. появляются только без сервиса, имитируя боль. Это spot-check, не непрерывный поток.
3. Tier unlock: требует reputation >= 60, quality >= 60 — косвенный кнут.

### Проблема баланса кнут/пряник

Убрав Pain Engine, авторы заменили «невидимые штрафы» на «видимые бонусы». Это правильная философия для прозрачности. Но нарушен принцип **Frustra Balance**: у игрока нет стимула искать защиту от рисков, которых нет. Если OFD не дёргает штрафы каждые 10 дней, зачем покупать ОФД ради -0.5% налогов при tax rate 6%? ROI ОФД: 12 000 ₽/год, экономия: ~0.5% от ~500K/год выручки = ~2 500 ₽/год. ОФД убыточен как покупка — только онбординг-нарратив мотивирует его взять.

**Калькуляция ROI по сервисам (приближённо, tier-1 магазин, ~500K/год выручки):**

| Сервис | Цена/год | Прямой эффект | Примерный ROI |
|---|---|---|---|
| Банк | 0 ₽ | +40% оплат → +~200K выручки | Бесконечный |
| Маркет | 24 000 ₽ | +20% capacity → +~40K выручки | ~1.7× |
| ОФД | 12 000 ₽ | -0.5% налогов → ~2 500 ₽ | 0.2× (убыточен) |
| Диадок | 24 000 ₽ | -0.5% налогов → ~2 500 ₽ | 0.1× (убыточен) |
| Фокус | 24 000 ₽ | +1 rep/day → качественный эффект | Неизмеримо |
| Эльба | 36 000 ₽ | -0.5% налогов + -35% энергии | Низкий без Pain |
| Экстерн | 24 000 ₽ | -2% налогов → ~10K/год | ~0.4× |

Без Pain Engine у OFD, Diadoc и Elba нет экономического обоснования покупки. Они существуют только как «нарратив о законопослушности» и как шаги к bundle-тиру. Bundle — единственное, что делает их покупку рациональной (но 3-сервисный bundle уже активируется с Банком + Маркетом + одним любым).

### Вывод по синергии

Bundle-тиры как единственная синергия — **чрезмерно упрощена для выбранного жанра**. У игрока нет выбора «купить этот или тот сервис сначала» — оптимальная стратегия детерминирована: Банк (бесплатно) → Маркет (ROI 1.7×) → любые 2 для bundle 3+ → потом Экстерн → заполнить до 7 для bundle 7+. Ни одна альтернативная последовательность не является жизнеспособной стратегией. Это нарушает **Transitive Balance**: все сервисы должны иметь нетривиальный cost-vs-benefit, а не только Банк и Маркет.

## 4. Прогрессия — businessTier 1–3 как единственная видимая прогрессия

### Текущие слои прогрессии

1. **businessTier 1→2→3** — единственная явная. Три ступени, gate по неделям/балансу/репутации/качеству. Мощный эффект: ×1.5–×2.5 клиентов, ×1.2–×2.5 чека.
2. **Онбординг (stages 0–4)** — разблокировка сервисов. Скрытая для игрока как «прогрессия», ощущается как туториал.
3. **Достижения (~30 штук)** — коллекция без механического эффекта. Компетентностный сигнал, но не прогрессия.
4. **qualityLevel 0–100** — слабо изменяется (±1/неделю от сотрудников), gate для tier-2 cafe/salon. Фактически вспомогательный параметр.
5. **reputation/loyalty 0–100** — gate для tier upgrades, постоянный операционный параметр.

### Проблема

**Зазор между tier-апгрейдами огромен.** Tier-2 для магазина открывается на неделе 12 при балансе 200K. Tier-3 — на неделе 25 при балансе 700K. Это 13 недель между первым и вторым апгрейдом, 27 недель между вторым и третьим. В промежутках игрок наблюдает рост баланса — и ничего визуально нового не происходит.

По **Nested Loop Model** (30-сек / 5–15 мин / сессионный):
- Микро-петля (одна неделя): событие + кнопка — есть.
- Мезо-петля (5–10 недель): onboarding stage completion + «ощутил новый сервис» — слабая, онбординг почти не ощущается как достижение.
- Макро-петля (полный год): tier upgrade + victory — есть, но 3 ступени на 52 недели — очень скудно.

**Bartle's Achiever** ожидает видимые milestones и measurable progress. В текущей игре неделя 15–24 — практически «плато»: tier-2 куплен, tier-3 ещё недоступен, онбординг завершён. Единственный прогресс — цифра баланса растёт. Это **boredom zone** по Flow Model.

### Удалённые прогрессии и образовавшийся вакуум

Удалённые системы `level`/`experience` создавали micro-progress signal каждые 2–3 недели (level up). Их удаление оставило вакуум в мезо-петле. Текущие достижения частично заполняют его, но achievement не имеет механического эффекта — это читаемый сигнал без геймплейного последствия.

## 5. Дыры после удалений Phase A/B/C

### 5.1 Удалён Weekly Tactic Chooser

**Что делал:** 3 тактики на неделю создавали явный выбор стиля игры каждые 7 дней.
**Что осталось:** Нет. Единственный еженедельный выбор — событие (1 раз) плюс опциональные управленческие действия.
**Дыра:** Decision density в обычные недели (без событий) близка к нулю. Игрок нажимает «Следующая неделя» и ждёт результата.
**Что нужно «залить»:** Не возвращать тактики в прежнем виде, но добавить 1–2 активных решения в неделю: например, «Приоритет недели» (выбор фокуса между качеством, трафиком или маржой).

### 5.2 Удалён brandEffect

**Что делал:** Компаунд репутация+лояльность → невидимый множитель на всё.
**Что осталось:** reputation → clientModifier (шкала step-function: 0.5/0.7/0.9/1.0/1.1) + loyalty → capacity modifier (+10%/-15%) + loyalty decay above 70.
**Дыра:** Разрыв между «высокая репутация» и «ощутимый бонус» стал менее градуированным. На репутации 61–80 нет разницы: всё равно reputationModifier = 1.0. Игрок не получает сигнала, что рост с 65 до 79 что-то значит.
**Что нужно залить:** Сгладить step-function до линейной кривой в диапазоне 40–90.

### 5.3 Удалены SYNERGIES_CONFIG (7 пар)

**Что делал:** Предполагалось — пары-синергии давали специфические бонусы при комбинировании сервисов.
**Что осталось:** Bundle Tiers — один linearly graded bonus.
**Дыра:** Нет смыслового «почему Market + OFD дают что-то специфическое вместе». Контур-бренд строит нарратив «интегрированная экосистема», но в механике это просто «добавь ещё один к счётчику».
**Что нужно залить:** 2–3 именованных пары-синергии с нарративным обоснованием (Market+OFD = «автоматическая фискализация»: -1% налогов сверх базовых). Не семь невидимых пар, а три видимых с реальным эффектом.

### 5.4 Удалены поставщики (suppliers.ts)

**Что делал:** Выбор поставщика был ещё одним рычагом управления.
**Что осталось:** Ассортимент-категории, FIFO-склад. Выбора поставщика нет.
**Дыра:** Фокус теряет ключевую механическую функцию — «проверка поставщиков». Сервис описан как «проверка контрагентов», но контрагентов выбирать нельзя. Фокус стал «просто репутация +1/день».
**Что нужно залить:** Не восстанавливать полный поставщик-менеджмент, но добавить 1–2 события формата «Поставщик Х предлагает скидку 15%, проверить через Фокус?» с реальными последствиями провала без Фокуса.

### 5.5 Удалён Pain Engine как непрерывный поток

**Что делал:** Каждый отсутствующий сервис тихо вычитал деньги каждый день.
**Почему удалён:** Игрок не знал, когда и за что списания — «невидимая математика».
**Что осталось:** Pain = 0 в runtime. Видимый блок «Потеряно без Контура» в WeekResultsOverlay показывает данные, но расчёт всегда 0.
**Дыра критическая:** Сервисы ОФД, Диадок, Эльба не имеют экономического обоснования без Pain.
**Что нужно залить:** Не возвращать «невидимые штрафы», но восстановить Pain Engine как **дискретные события** (раз в N недель), видимые в WeekResults с объяснением: «Без ОФД пришёл штраф 18 000 ₽». Реализация PAIN_LOSSES уже есть в gameBalance.ts — нужно только подключить к eventGenerator вместо processWeek.

### 5.6 Удалены NPC-цепочки (6 штук → 2)

**Что было:** 6 NPC-цепочек с конкретными stakes (viktor_loan, gleb_review, anna_war и т.д.).
**Что осталось:** 2 цепочки (mikhail_crisis, legacy) + 8 трёхэпизодных арок.
**Дыра:** Арки хорошо написаны нарративно, но их механические эффекты малы (±репутация, ±лояльность). Ни одна арка не создаёт game-changing дилемму, сопоставимую с «крупным кризисом» типа viktor_loan. mikhail_crisis и legacy — хорошее начало, но два крупных кризиса на 52 недели мало.
**Что нужно залить:** Добавить 1–2 «горячих» NPC-события с реальными stake (потеря ключевого поставщика, уход команды, конкурентный захват аудитории), которые происходят в середине игры (недели 15–30) и требуют от игрока активного выбора с значимыми последствиями.

## 6. Топ-7 рекомендаций (приоритизированы)

### P1. Восстановить Pain Engine как дискретные события (критично)

**Проблема:** ОФД, Диадок, Эльба экономически убыточны без Pain. Игрок берёт их ради bundle-тира, не из-за их ценности.

**Решение:** Переместить PAIN_LOSSES из runtime-цикла в `eventGenerator`. Каждый отсутствующий сервис с определённой вероятностью в неделю генерирует событие-штраф из пула (кризисные события уже используют этот паттерн: noService: 'fokus'). Событие видимо, объяснено, предсказуемо по нарративу. Пример: «Без ОФД: налоговая прислала уведомление, штраф 15% от выручки недели». Это сохраняет прозрачность (игрок знает, за что списание) и восстанавливает стимул.

**Теория:** Frustra Balance — ощущение риска важно для покупки «страховых» сервисов. Без него Discovery Aesthetic исчезает.

**Реализация:** Подключить массив `PAIN_LOSSES` из gameBalance.ts к `generateEvent` с флагом `noService`. Рефакторинг минимален — инфраструктура готова.

### P2. Добавить «Приоритет недели» (Weekly Focus) — лёгкий еженедельный выбор (высокий приоритет)

**Проблема:** Недели без событий — режим таймера. Decision density в обычные недели = 1 кнопка.

**Решение:** Перед каждой неделей игрок выбирает фокус из 3 опций (не 3 тактики, а мягкий вектор):
- **Трафик:** клиенты +8%, репутация −1
- **Качество:** loyalty +3, трафик −5%
- **Маржа:** средний чек +5%, новые клиенты −10%

Фокус активен только одну неделю, отображается в KPI-области. Выбор быстрый (5 секунд), но значимый — формирует стиль игры, не блокирует.

**Теория:** SDT Autonomy — игрок должен чувствовать, что его еженедельные решения имеют значение. По Nested Loop: мезо-петля (5–15 мин) получает осмысленный цикл выбора.

**Почему не тот же «тактик-чузер»:** Тактики блокировали неделю до выбора и имели широкий эффект. Weekly Focus — легче, быстрее, не блокирует прогресс.

### P3. Исправить экономику ОФД как первого обязательного сервиса (высокий приоритет)

**Проблема:** ОФД стоит 12 000 ₽/год, даёт -0.5% налогов (~2 500 ₽/год при 500K выручке). Убыточен экономически. Онбординг говорит «без ОФД штраф за каждый чек», но это не реализовано.

**Решение (два варианта):**

*Вариант A — Реализовать штраф:* Без активного ОФД после онбординг-стейджа 1, раз в 2–3 недели: событие «Налоговая проверка кассы: −18 000 ₽» (или Контур-опция: «Есть ОФД — проблем нет»). Это наиболее соответствует нарративу.

*Вариант B — Пересмотреть цену ОФД:* Снизить до 6 000 ₽/год или поднять taxSaving до 1.5%, сделав сервис хотя бы break-even. Менее интересен нарративно.

**Рекомендую Вариант A** — он восстанавливает Discovery Aesthetic и нарративную честность.

### P4. Добавить 3 именованных пары-синергии (средний приоритет)

**Проблема:** Bundle Tier — единственная синергия. Нет смыслового «почему эти два сервиса вместе сильнее».

**Решение:** Добавить 3 видимые пары с нарративным обоснованием и небольшим специфическим эффектом:
1. **Маркет + ОФД** = «Автоматическая фискализация»: -1% налогов (автоматический учёт → меньше ошибок).
2. **Банк + Эльба** = «Расчётный счёт + бухгалтерия»: -10% acquiring fee (интеграция снижает комиссию с 1.5% до 1.35%).
3. **Фокус + Диадок** = «Проверен + подписан»: +2 репутации за каждого нового поставщика (проверил и сразу подписал электронно).

Пары маленькие, не game-breaking. Их ценность — нарративная «ага-момент», когда игрок понимает логику экосистемы Контура.

**Теория:** По Quantic Foundry, Mastery и Discovery мотивации поддерживаются через «скрытую глубину, которую нужно найти». Три видимые пары создают лёгкий оптимизационный пазл.

### P5. Добавить мезо-прогрессию — «Сигнальные события» каждые 4–6 недель (средний приоритет)

**Проблема:** Между tier-апгрейдами (недели 12 и 25) — плато без нового визуального прогресса. Boredom zone по Flow Model.

**Решение:** Каждые 4–6 недель — одно из следующих событий:
- Разблокировка нового типа рекламы (уже есть частично через онбординг).
- NPC переходит в следующий эпизод арки (уже есть, но игрок не видит «прогресс арки» как прогрессию).
- Город-газета (заготовка `cityNewspaper.ts` есть) публикует заметку о бизнесе игрока — небольшой +rep + нарративный milestone.
- Разблокировка новой категории ассортимента (некоторые требуют оборудование + сервис — это уже gate).

**Ключевое:** Сделать эти события **явно видимыми как прогрессия** — небольшой celebration card, аналогичный tier upgrade. Игрок должен ощущать «что-то новое открылось» каждые 5–6 недель, а не только при tier upgrade.

### P6. Исправить репутационную функцию — сгладить step-function (низкий приоритет)

**Проблема:** `getReputationModifier` возвращает 5 значений (0.5/0.7/0.9/1.0/1.1). Рост репутации с 61 до 79 не имеет никакого эффекта (оба дают 1.0). Игрок не получает feedback на управление репутацией.

**Решение:** Линейная кривая в ключевом диапазоне:
```
rep < 20: 0.5
20–40: линейно 0.5→0.8
40–70: линейно 0.8→1.0
70–90: линейно 1.0→1.1
90–100: 1.1
```

Это создаёт непрерывный feedback-сигнал: каждые 5 очков репутации ощутимо меняют клиентопоток. Соответствует принципу **Feedback Clarity** из Flow Model — каждое действие должно иметь readable consequence.

### P7. Удалить мёртвый код `LEVEL_TABLE` и привести `PAIN_LOSSES` в соответствие с runtime (низкий приоритет, техническое)

**Проблема:** `LEVEL_TABLE` в `business.ts` (строки 274–285) — полная таблица опыта для удалённой системы. `PAIN_LOSSES` в gameBalance.ts — откалиброванные числа для нулевого engine.

**Решение:**
- Удалить `LEVEL_TABLE` полностью — нет читателей в runtime.
- Либо подключить `PAIN_LOSSES` к реализации (см. P1), либо удалить и его, чтобы не вводить в заблуждение разработчиков.

**Теория:** «Мёртвый код — это ложная карта». Разработчик, читающий `PAIN_LOSSES`, будет считать, что pain работает.

|---|---|---|
